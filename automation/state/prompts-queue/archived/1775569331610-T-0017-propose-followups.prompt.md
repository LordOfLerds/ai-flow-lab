# T-0017 Spec

## Task metadata
- **task_id**: T-0017
- **title**: Score goes higher while player not moving  
- **lane_type**: feature-lane
- **executor**: codex

## Problem statement
The current score system increases unconditionally every frame (line ~1034: `gs.score += 1;`), regardless of whether the player is making meaningful progress through the level. This results in the score continuously climbing even when the player is standing still, moving backwards, or otherwise not advancing through the game.

## Source of truth
Current code in `index.html` shows the score update logic in the main update loop:
```javascript
// ── Score ──
gs.score += 1;
```

This increment happens every frame during the playing phase, independent of player movement or progress.

## Desired behavior
Score should only advance when the player is making forward progress through the level:
- Score increases only when player moves rightward (positive x-direction)
- Score remains static when player is stationary
- Score does not increase when player moves backwards/leftward
- Other score sources (coins: +50, gems: +200, enemies: +100, level completion: +500) remain unchanged

## Constraints
- Preserve all existing score mechanics for pickups, enemies, and level completion
- Maintain current score values and balance for non-movement scoring
- Use minimal, focused changes to existing game logic
- Do not alter camera, movement, or collision systems
- Respect existing game architecture and coding patterns

## Acceptance criteria
1. Score does not increase when player velocity is zero (`p.vx === 0`)
2. Score does not increase when player moves leftward (`p.vx < 0`) 
3. Score increases at reasonable rate when player moves rightward (`p.vx > 0`)
4. All other score sources (coins, gems, enemy kills, level completion) continue to function identically
5. Score advancement rate during normal rightward movement feels appropriate for game balance
6. No regression in existing game mechanics or visual feedback

## Risks
- **Game balance**: Players may perceive reduced score progression if they frequently pause or backtrack
- **Player experience**: Could discourage exploration or careful platforming if score only rewards constant forward movement
- **Edge cases**: Rapid direction changes or very small movements might cause score to stutter unexpectedly

## Open questions
1. Should score advance proportionally to movement speed, or at a fixed rate when moving forward?
2. Is there a minimum velocity threshold below which score should not advance (to avoid micro-movements)?
3. Should score advancement be based on actual position change rather than velocity to handle collision edge cases?
4. How should this interact with dash mechanics where player may have high velocity but brief duration?
