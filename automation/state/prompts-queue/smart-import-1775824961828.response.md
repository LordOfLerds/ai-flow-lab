Business purpose

aurena-k-list is a local operator-facing review system for converting accounting-style K-list imports into an auditable working list of purchase cases that can be reconciled against Bidware auction revenue, unresolved lots, and finally Dropbox/Paper contract review.

The real business object is not an auction. It is a purchase case derived from accounting/export data and then enriched through multiple review steps.

Core business entities
1. PurchaseCase

Primary operational entity. In code this is centered around the domain model in src/klist/domain/models.py, with import creation in src/klist/import_pipeline/importer.py.

Business meaning:

One economic case derived from one accounting document block (Beleg-Nr) from the K-list import.

It may later map to zero, one, or multiple Bidware auctions.

It may end with values coming from auction revenue, Dropbox fallback, or remain blocked for review.

Important fields/business concepts:

purchase_name_raw: visible case label from the K-list, often containing insolvency markers like IV, MV, law firm names, etc.

tax_type: current tax classification path (normal, differential, mixed, etc., depending on the implemented enum).

initial_value_net, initial_value_diff: starting value buckets.

current_value_net, current_value_diff: effective current values after revenue decisions and/or Dropbox final remaining value.

status: workflow state, not just UI decoration.

excluded, excluded_reason: terminal non-operational handling for cases like cars or other out-of-scope items.

dropbox_checked, dropbox_manual_rest_value: manual fallback information.

2. ImportBatch

Represents one uploaded K-list import run. Persisted through import batch metadata and source references; see import persistence and repositories under:

src/klist/import_pipeline/persistence.py

src/klist/repository/batch_repo.py

src/klist/repository/schema.sql

Business meaning:

A traceable import event tied to one source workbook.

Must prevent accidental duplicate import of the same file or overlapping accounting blocks.

Important real-world rule:

Re-import of the same content must be blocked.

Overlapping Beleg-Nr blocks across imports must be treated conservatively and not silently duplicated.

Real business rules not obvious from code alone
K-list parsing and accounting semantics

The import source is an accounting-style export, not a business-friendly case list. Important source patterns:

Beleg-Nr groups a document block.

Customer/debtor anchors are derived from Kto-Nr prefixes like 305, 306, 308, 309.

BC='H' customer rows anchor purchase-case creation.

Tax meaning is not always on the anchor row; sometimes it emerges only from the whole block.

Blank Sy and blank Steuer

This is now a hard business rule, not just a hint:

If both are blank in the relevant imported case context:

Sy blank

Steuer blank

then the case is auto-classified as differential taxed and proceeds through the differential bucket path.

This is an explicit domain decision, not something that should be casually changed by future automation work.

Duplicate names are not simple duplicates

Repeated names may mean:

storno / reversal

follow-up payment / additive booking

distinct but similar cases

The system should recognize and explain these patterns, but final interpretation remains manual unless a separate signed-off rule is introduced.

IV, MV, Masseverwalter names

These are not noise in the business sense. They are often part of the raw accounting/legal identity of the case. The visible UI should preserve the real-world raw label even if internal search variants later strip or normalize pieces for Bidware lookup.

Lifecycle / state transitions (business interpretation)

States exist in code in src/klist/domain/models.py and transition logic in src/klist/domain/transitions.py. Business interpretation:

imported_from_k_list: raw imported case exists

classification_pending: tax/business meaning still requires human review

duplicate_conflict: repeated-name case requires review

ready_for_bidware_search: safe to search in Bidware

bidware_no_match: Bidware was searched and found nothing

bidware_candidates_found: candidates harvested but not yet confirmed

auctions_confirmed: at least one auction explicitly linked

revenue_action_pending: revenue decisions now exist / revenue path active

lot_review_pending: relevant unsold >5000 lots need manual review

manual_rest_value_entered: Dropbox final remaining value entered

excluded: intentionally out of operational flow

completed: conceptually available, but historically has been less central than readiness logic; readiness currently matters more than this label alone

Real-world constraints and edge cases

Included lots still block export
This is intentional in V1 because the downstream effect of included lots on final financial values is not yet automated.

No-match is not an error
It is a valid business state that routes into manual fallback.

Export readiness is not the same as “nice-looking case”
A case can look operationally complete in UI but still be blocked because required manual steps were not done.

Exclusion is irreversible in V1
This is a deliberate policy choice to reduce late-stage accidental reopening of cases.

Bestandsliste import is not yet a finished business flow
The current implemented core is K-list driven. Any references to inventory/bestands import should be treated as incomplete unless verified in current code.
