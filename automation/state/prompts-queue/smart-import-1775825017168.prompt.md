## What Claude Already Knows (from code analysis)

**aurena-k-list** — 106 files
Technologies: Python
This is a Python web application that automates the processing of K-list purchase cases by importing Excel files, searching for matching auctions via Bidware using Playwright automation, allowing users to review and confirm matches, calculating revenue decisions, performing lot checks against specific criteria (unsold lots with reserve price > 5000), and finally exporting the processed results back to Excel. The application uses FastAPI with server-side rendering, SQLite for persistence, and follows a clean architecture with domain models, service layers, and repository patterns, ensuring all business-critical decisions (auction matches, revenue calculations) require explicit user confirmation rather than automation.

### Core Patterns

**Domain-Driven Design**: Pure domain models in `domain/` with no I/O dependencies. Business logic and state transitions isolated from infrastructure.

**Repository Pattern**: All SQL isolated in `repository/` modules. No ORM - raw SQL with explicit queries for performance and clarity.

**Service Layer**: Each major workflow (import, matching, review, export) encapsulated in dedicated service modules with clear boundaries.

**Adapter Pattern**: External systems (Bidware) wrapped in thin adapters that isolate selectors, timing, and parsing logic.

### Data Flow

1. **Import**: Excel K-list → `import_pipeline` → SQLite `purchase_cases`
2. **Matching**: Cases → `matching_engine` → Bidware search → `auction_candidates` 
3. **Review**: Candidates → `review_service` → User confirmation → `confirmed_matches`
4. **Revenue**: Matches → `valuation_service` → User decision → `revenue_decisions`
5. **Lot Check**: Cases → `lot_check_service` → Filter lots → `lot_candidates`
6. **Export**: Completed cases → `export_service` → Final Excel

### Invariants (draft)
### Business Rule Invariants

**Purchase Case Identity**: Cases with identical `purchase_name` are NEVER automatically merged. Always flagged for manual review to prevent data loss.

**Revenue Decision Required**: Revenue calculations are NEVER auto-applied. User must explicitly choose action via `RevenueAction` enum.

**Tax Classification**: Mixed tax types (`MIXED_TAX`) force manual classification - system cannot auto-determine correct rate.

**Lot Filter Criteria**: Lot checking only considers lots where `status = "nicht verkauft"` AND `Rufpreis > 5000`. Hard-coded business rule.

**Status Progression**: Case status follows strict state machine defined in `transitions.py`. Invalid transitions are prevented.

**Single Batch Import**: Each Excel file creates exactly one `ImportBatch`. Cases belong to exactly one batch.

### Data Integrity Invariants

**Foreign Key Constraints**: All relationships enforced at application level since using raw SQL without ORM.

**Decimal Precision**: Financial amounts stored with sufficient precision for currency calculations (typically 2 decimal places).

**Unique Identifiers**: All entity IDs are UUIDs to prevent collisions across import batches.

**Audit Trail**: All user decisions (auction confirmations, revenue actions) capture `decided_by` and `decided_at` for traceability.

### Search and Matching Invariants

**Bidware Read-Only**: Adapter only performs read operations on Bidware. No data modification allowed.

**Search Variant Generation**: Multiple search variants generated per case to improve match recall, but deduplication applied to results.

**Confidence Scoring**: All auction candidates include confidence score, but final match decision always requires human confirmation.

**Timeout Protection**: Bidware searches have timeouts to prevent hanging on unresponsive auction site.
